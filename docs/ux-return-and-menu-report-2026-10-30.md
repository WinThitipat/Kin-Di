## การลดงานที่ดูเป็น AI slop

- เพิ่มข้อมูลที่นำไปเลือกอาหารต่อได้จริง แทนข้อความตกแต่ง การ์ดใหม่ หรือแถบสถิติที่ไม่มีประโยชน์
- ใช้ภาษา “มีครบตามรายการที่เลือกไว้” และ “ยังไม่ได้เลือก … อย่าง” แทนการรับรองว่าทำได้หรือปลอดภัยแน่นอน
- ไม่สมมติว่าผู้ใช้มีไข่ ข้าว หมู กะเพรา หรือเครื่องปรุงอยู่แล้ว ผู้ใช้เลือกเครื่องปรุงพื้นฐานเองและระบบจำการเลือกนั้น
- ใช้ระบบกรองอาหารและประวัติเดิม ไม่สร้างระบบคู่ขนานหรือเพิ่ม dependency

### Motion review

| ก่อน | หลัง |
| --- | --- |
| ผลสุ่มไม่มีข้อมูลตู้เย็น | เพิ่มข้อมูลในแผงผลเดิม ไม่มีเอฟเฟกต์เข้าหรือกระพริบเพิ่ม |
| เปิดไพ่และสับไพ่ตาม motion เดิม | คง timing และ reduced-motion เดิม ไม่ยืดเวลาเพื่อโชว์ข้อมูลเพิ่ม |

## การตรวจสอบ

- Unit/API tests: 57 ข้อผ่าน รวมกรณี localStorage เสีย/ถูกบล็อก รายการว่าง เมนูน้อย และข้อจำกัดอาหาร
- Production build ผ่าน
- Browser flow ที่ 320, 390, 768, 1440px: เลือกของ → รีเฟรช → กลับหน้าสุ่ม → เปิดไพ่ → แสดงครบ/ขาด; ไม่พบแนวนอนล้นหรือ page error ในกรณีที่ทดสอบ
- นำเข้า 7 เมนูสำเร็จ ตรวจ URL รูปใน Storage ตอบ 200 และ API คืนทั้งหมด 24 เมนู

## ข้อจำกัดที่ยังมี

- จำตู้เย็นและประวัติในอุปกรณ์/เบราว์เซอร์นี้ ไม่ได้ sync ข้ามอุปกรณ์ และยังไม่มีการ merge การแก้ตู้เย็นพร้อมกันหลายแท็บ
- การเทียบไม่ตรวจปริมาณ วันหมดอายุ การปนเปื้อน หรือความครบถ้วนของสูตรต้นทาง เครื่องปรุงที่เลือกว่ามีพื้นฐานจะนับเฉพาะ IDs ที่ระบบกำหนด; เครื่องปรุง custom ไม่ถูกเดาว่ามีแล้ว
- “ครบ” อาศัยรายการวัตถุดิบในฐานข้อมูล ไม่ใช่การยืนยันความปลอดภัย; ตัวกรองอาหารทำงานแยกตามกติกาเดิม
- ลดซ้ำเป็นการจัดลำดับ ไม่ใช่ห้ามซ้ำเด็ดขาด ถ้าเหลือเมนูน้อยต้องยังสุ่มได้
- ยังไม่ได้ติด analytics จึงไม่อ้างว่าจำนวนคนใช้หรืออัตรากลับมาใช้เพิ่มขึ้นแล้ว
